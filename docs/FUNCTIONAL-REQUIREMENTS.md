# Seqcall: Functional Requirements

Scope: Seqcall analyses **JavaScript/TypeScript**, **C#** (sidecar, docs/CSHARP-SIDECAR.md) and **PHP** (FR-18)
and runs in **VS Code**, JetBrains IDEs (FR-15) and Vim / Neovim (FR-21). Requirements are written
language-neutrally where possible; they state rules, not cases from particular projects. Where a concrete case
helps, it links a neutral code sample in [req-examples/](req-examples/README.md).

Priority (MoSCoW): **M** = Must, **S** = Should (if feasible), **C** = Could (later).
IDs are referenced from tests (`FR-x.y` in test names) for traceability.

## Glossary

- **Participant**: an object (or class, for static calls / module) drawn as a box at the top with a lifeline.
- **Message**: an arrow between lifelines representing a call at a specific call site.
- **Found message**: a message with no sender (starts from a gate on the diagram edge) representing the entry into the root method.
- **Root method**: the method the diagram currently describes.
- **Expandable**: a message whose target method has a body in the analysed project.
- **Library call**: a call whose target is declared outside the project sources (node_modules, lib.d.ts).

## FR-1 Diagram generation

| ID | Pri | Requirement |
|---|---|---|
| FR-1.1 | M | When the user places the cursor / selects a line inside a method or function body and invokes **Show Sequence Diagram** (command palette, editor context menu, keybinding), the system draws the diagram of the *enclosing* method, beginning with a found message to that method's participant. |
| FR-1.2 | M | Supported callables: class instance methods, static methods, constructors, getters/setters, top-level functions, and functions assigned to `const` (arrow/function expressions). Module-level functions belong to a participant representing the module (stereotype «module»). A method seen through a type that maps a class's methods (`withCancel(new OrderApi())`: `Cancellable<OrderApi>`, each method a `CancellableFn<A, R>`) is still that method — `orderApi.listOrders()` → `OrderApi.listOrders`, not *unknown*. (example: [req-examples/FR-1.2](req-examples/FR-1.2.md)) |
| FR-1.3 | M | The initial diagram shows the direct calls of the root method (depth 1). The default depth is configurable (`seqcall.defaultDepth`). |
| FR-1.4 | M | Messages appear in evaluation order: calls nested in arguments or receivers precede the enclosing call; statements in source order. |
| FR-1.5 | M | Calls to `this`/`super` methods are drawn as self-messages with a nested activation bar. |
| FR-1.6 | M | Library calls are hidden by default; a toolbar toggle shows them (targets grouped per library as «external» participants). |
| FR-1.7 | S | **Follow cursor** mode: when enabled, moving the cursor into a different method redraws the diagram for that method automatically (debounced). |
| FR-1.8 | M | Calls whose target cannot be resolved (`any`, dynamic access) are drawn to an «unknown» participant, labelled with the call expression text, and are not expandable. |
| FR-1.9 | S | `await`ed / promise-returning calls are drawn as normal messages with an `async` marker. Callbacks passed as arguments: FR-1.11, FR-1.13. |
| FR-1.10 | S | **Combined fragments**: calls inside control flow of the shown method body are framed — `alt` (if/else-if/else chains, `switch` (one operand per case group, `default` = `[else]`), conditional expressions, C# switch expressions), `opt` (single guarded branch), `loop` (for, for-of/in, foreach, while, do; guard = condition or `each x of xs`), `try` (try block + one `[catch …]` operand per catch clause; `finally` not framed). Guards are the abbreviated source condition (tooltip: full text). Frames nest and belong to the activation of the message whose body they are in. Only fragments with visible messages are drawn: empty operands are dropped, an `alt` with one visible branch is drawn as `opt` (else → negated condition), `opt [a]` directly around `opt [b]` merges into `opt [a && b]`, a `try` without a visible catch call is not drawn. Clicking a frame's tag / a guard reveals the condition in the editor. Toolbar toggle **Fragments** and setting `seqcall.showFragments` (default on). Message ids are unchanged (frames are derived, no state). **Frames are tinted areas in their kind's colour** (loop blue, alt / opt purple, try red, callback green; faint fill, border and tag in that colour) so they read as regions, not as lines like the calls; a guard whose corner tag is not right beside it (a wide frame, an operand further down) is preceded by the kind in that colour: `loop [each $item of …]`, `alt [else]`. |
| FR-1.12 | S | **Minimize / restore fragments**: the ⊖ after a frame's guard (quiet until hovered) minimizes the fragment to one dashed row — tag, first guard, `⋯ n calls`, ⊕. Its calls (and participants only they reach) leave the sequence and the class diagram; clicking the count or ⊕ restores it. Nested fragments are folded with their outer one; a minimized inner fragment stays inside its outer frame. State per diagram, kept across refresh, collapse/expand of the owning call and re-rooting; ignored while **Fragments** is off. Fragment ids are `<owner>#<kind><nesting>@<ordinal of the first call>` (stable like message ids). |
| FR-1.13 | S | **Delegate / function parameters**: invoking a parameter of delegate or function type (`onSuccess(x)`, `onSuccess.Invoke(x)`, `cb(x)`) is resolved through the argument→parameter binding to the method the caller passed (method group / function reference such as `Mapper.toDto`, `this.handle`, `f.bind(this)`), also when the parameter is passed on through further calls. It is drawn as a normal call to that method's participant (expandable, navigable, in the class diagram), labelled `onSuccess ⇒ MapToDto(…)`. When the caller passed a lambda or the caller is not in the diagram, it is a self-call `ƒ onSuccess(…)` (tooltip says why) — never «unknown». Message ids stay `…/<ordinal>:<parameter name>`. When the parameter's declared type is a named project type (a function type alias / interface, a C# `delegate` type — not `Func`/`Action`), that type is the **port**: the class diagram draws the sender's dependency to «interface» `BranchLister` (members = invoked parameters) and the implementation's realization of it, instead of a dependency on whatever interface the caller's expression named (e.g. an adapter's `Host` bundling the ports) — so hexagonal code shows no false layer violation. |
| FR-1.11 | S | **Lambdas and callbacks.** A lambda passed to a *library* (or unresolvable) function is drawn inline: its calls follow the receiving call, framed `loop [each u of users]` for iteration methods (`forEach`, `map`, `filter`, `reduce`, `some`, … — chains shown as `users.filter(…)`) or `callback [promise.then]` otherwise; frames nest, combine with the body's own fragments and can be minimized (FR-1.12). A lambda passed to a *project* function is not inlined: where that function invokes the parameter (FR-1.13), the `ƒ` message goes back to the object that wrote the lambda and expands to its body, which sees the writer's fields / parameters / locals plus its own parameters bound to the invocation's arguments. TypeScript and C# (LINQ `Where`/`Select`/`Any`/…, `List.ForEach`/`Find`/…: `loop [each u in users]`; `ContinueWith`, `Task.Run`, …: `callback`). Expand all / Expand all below / Expand everything open an invoked lambda like any other call, and Smart expand opens a lambda invoked by an open method (its own logic), so the calls a closure makes are shown like the method's other calls. TS: a callback frame says **when** it runs where the code tells: React effects by their dependencies (`useEffect: when id changes`, `on mount`, `after every render`), `useMemo`, `useCallback: when called`, timers (`setInterval: every 5000 ms`, `setTimeout: after …`), `addEventListener: on resize`; the order of frames is the order in the code, not the order they run. A handler given to a JSX prop is drawn where the prop is: written in place (`onClick={async () => …}`) or a function local to the component passed by name (`const onSave = () => …` → `onClick={onSave}`, drawn at its first prop only), framed `callback [SaveButton onClick: on click]` (event props say the event, others just the prop: `List renderItem`); a `useCallback` handler stays at `useCallback`, a handler from props is not drawn. PHP: a project method that wraps a closure in another one and returns it, invoked at once (`$this->guard('…', function () {…})($x)`), is drawn as the sender's own call `guard(…)` (not `unknown`), the closure's calls follow it in `callback [guard(…)(…)]`. |
| FR-1.15 | S | **Early exits**: a `return` / `throw` that is not in tail position (the method may continue after it on another path) is a small muted marker on the method's activation bar, in a half-height row where it happens: `↩ [!user]`, `↯ [!valid] ValidationException` (throws in red). The marker joins the frame of its `if` / `switch` / `catch` when that frame is drawn (then it shows no guard of its own), but never creates a frame: a guard clause without visible calls is just the marker with its condition. Tail returns, returns inside lambdas and `?? throw` expressions are not markers. Click → the statement; hover card says "Returns early when …" / "Throws X when …". Shown with **Fragments** (off → no markers). |
| FR-1.14 | C | Return messages: not drawn; result labels (FR-9.4/9.5) show results instead (a return arrow costs a row). Only on demand. |
| FR-1.16 | S | **Guards in wide frames**: a guard is drawn next to the first call it guards (right of the owner's activation bar), even when the frame reaches far to the left or right (it encloses those participants). When more than half of a guard is scrolled out of view while its frame line is on screen, a copy floats at the edge of the view inside the frame — `[guard] →` / `← [guard]`, with the frame's kind (`← opt [order.Id is null]`) when its tag is out of view too — on a background that hides the cut-off rest of the real guard; clicking it scrolls to the real guard. Nothing is drawn twice while the guard is visible. |
| FR-1.17 | S | **What a catch does with the error**: every `catch` clause of a drawn `try` says, after its guard, what happens to the error — `swallowed` (amber, with tooltip: the caller never learns it failed), `↩ <value>` (the error becomes a return value), `skipped` (`continue`), each prefixed `logged,` when the clause calls a logger (`_logger.LogError`, `Log::warning`, `console.error`, `report($e)`, …; not `login`). A catch without visible calls (only logging / library calls) is no operand but a guard-only row at the bottom of the frame, so a `try` whose catch swallows the error is drawn even though nothing inside the catch is visible (example: [req-examples/FR-1.17](req-examples/FR-1.17.md)). A catch that rethrows (`throw`) adds nothing; a `try` whose catches all rethrow is not drawn without visible catch calls. Judged from syntax by all three adapters (statements in nested lambdas do not count; `FragmentScope.handlers`, protocol `Fragment.catches`, `FragmentOperand.outcome`). Rows of such catches follow the visible operands, not their source order. |
| FR-1.18 | S | **Getters and setters are steps** (TS, C#; PHP Eloquent accessors: FR-18.15): reading a property that is a getter of the project (`this.orders`, `this.openOrders.filter(…)`, C# `order.Total` with `Total => …` / `get { … }`) runs it, and so does assigning a project setter (`b.rating = 5`): drawn as `«get» orders` / `«set» rating` (no argument list), expandable into the accessor's body like any call, in evaluation order (a setter after the assigned value; C# `+=` reads and writes). Plain fields, auto-properties (`{ get; set; }`), method calls, `nameof` and library accessors are not; C# object initializers (`new Order { Total = 5 }`) are not drawn but count as callers. Show callers of an accessor lists those reads / assignments (FR-4.1). C#: a property read through an interface (no body) is not a step. |
| FR-1.19 | S | **Calls on values typed `any`** (TS): (a) a project function's parameter declared `any` / `unknown` (`#parseResponse(schema: any, …)`) takes the **type of the argument the caller passes** in the shown flow (also passed on through further `any` parameters): a library type (zod's `ZodObject`) makes `schema.parse(…)` a library call — hidden by default, its package with *Library calls* — a project type sends it to that class (`:Schema`). (b) A call still unresolved says **why** in its hover card: `` `schema` is typed any, so what it calls cannot be known `` (give it a type, or open the flow from a caller that passes a typed value), else *its declaration was not found* (a library not installed, packages not restored, or a dynamic call). Not covered: a project type's method is not expandable through such a call; C# / PHP give only reason (b)'s second form. That reason names what is missing in the call's language: `node_modules` for TS / JS, `vendor/` (composer install) or a property / variable set from the container without a declared type for PHP, packages not restored (dotnet restore) for C#. (c) **String / Number methods on a value typed any** (`path.toLowerCase().startsWith('http')` on an untyped JS parameter) are the built-ins — library calls like on a typed string, hidden by default, shown with *Library calls*; only names String / Number alone have (`toLowerCase`, `startsWith`, `trim`, `split`, `padStart`, `toFixed`, …): `get`, `find`, `map`, `replace`, `match`, `includes`, `slice`, `toString` stay unknown, since project objects use them too. |
| FR-1.20 | S | **React child components as messages** (TS): a JSX element of a **project component** (`<OrderList orderIds={ids} {...rest} />`) is a message from the component that renders it, labelled `«render» OrderList(orderIds, ...rest)` (props by name; tooltip `<OrderList orderIds {...rest} />`), named by its tag (`OrderRow`, not the `_OrderRow` that `observer(_OrderRow)` wraps), drawn before the calls in its props and children, expandable to the component's own calls. Resolved like pages (FR-16.6): through `observer` / `memo` / `forwardRef`, `const X = observer(Inner)`, default exports; a class component to its `render` (one «static» lifeline per class). Only project code that renders JSX: DOM elements, library components and styled components (`Styled.Wrapper`) are not drawn. (example: [req-examples/FR-1.20](req-examples/FR-1.20.md)) `cond && <X />` is an `opt [cond]` frame (only when the right side is JSX; `&&` between calls stays unframed), `?:` an alt, `.map(…)` a loop. **Show callers** (FR-4.1) and **paths to here** (FR-22) of a function component include the elements that render it, also through `const X = observer(_X)` and `export default memo(X)`. *I/O in a loop* (FR-19) skips I/O in a JSX handler written inside the loop (`ids.map((id) => <Row onDelete={() => api.remove(id)} />)` runs on a user action), not a loop inside a handler (`onClick={() => ids.forEach(api.remove)}`). Cost: whole-project walks (findings sweep) go deeper; opening one diagram is not slower. |
| FR-1.21 | S | **C# 14 extension blocks** (`extension(Payload p) { Request ToRequest() … }`): a call to a member of an extension block is a static call on the static class that holds the block, exactly like a classic extension method — the receiver is the first argument, the key is the classic one (`Ext.ToRequest(Payload)`), the lifeline is `Ext «static»`. Static members of a block (`User.Guest()`) and generic blocks (`extension<T>(IReadOnlyList<T> items)`) too. Go to definition, expanding, callers and type uses work on the member's own code; the class box lists the members like classic ones (`ToDto(this User user): UserDto`, static). |
| FR-1.22 | S | **Follow this case**: right-click the guard of an `alt` branch (if / else-if / else, `switch` case, `match` arm) → *Follow this case*: the other cases leave both diagrams (their calls, exits and the participants only they reach); the frame stays an `alt` with that one branch and says `📌 2 other cases` after the guard — a click on it, or *Show all cases* on the guard, brings them back. For business variants that no heuristic can choose (`shipping == Express`, a customer tier): read one scenario at a time. Combines with Smart expand (FR-3.9, which does not choose among variants) and minimized fragments. Kept per diagram (refresh, focus and re-root move it with the calls below, shared states carry it, a followed case not found is reported). Only with **Fragments** on. |
| FR-1.23 | S | **A function handed on to a library runs there**: a function parameter (a closure or method the caller passed, FR-1.13) that the method hands to a library or unresolved call (`->then($work)`, `promise.then(cb)`, a lock's or queue's callback) is drawn right after that call as the invocation of the parameter (`ƒ $work`), back to the object that wrote the closure, its body below — so a flow whose work is inside a closure run by a lock, a transaction or a promise shows that work. Its parameters come from the library (not bound). A method whose only visible content is such a hand-over is expandable. |

## FR-3 Expand / collapse

| ID | Pri | Requirement |
|---|---|---|
| FR-3.1 | M | Expandable messages show an expand affordance; expanding inserts the target method's calls as nested messages (sent from the target's lifeline, inside its activation bar). |
| FR-3.2 | M | Expanded messages can be collapsed, removing their nested subtree; participants no longer referenced by any visible message disappear. |
| FR-3.3 | S | **Expand all** (✦ ▾ menu, FR-3.12; with ↯ on it leaves the error branches folded) opens *every* call, level by level (breadth-first, so a limit leaves a complete shallow picture), up to 500 messages and 12 levels; its ▾ (and the canvas menu) offers **One more level**. When a limit stops it, a closable strip says why ("Stopped at 498 messages (limit 500) — 37 calls still folded" / "Reached the depth limit (6 levels)") with *One more level*, *Overview instead*, *Collapse all*. *Collapse all* goes back to depth 1. The strip counts only calls Expand all could open: the DI container step (FR-8.7) and calls under a *Don't expand* rule are not "still folded". *One more level* is asked for by hand, so it goes past the depth limit (the render limit still holds). |
| FR-3.7 | S | **Expand all below** a call: Shift+click on its ⊕, or the message menu (*Show from here ▸ Expand all*, hint "Shift+click ⊕") — everything below that call, the rest of the diagram unchanged, same limits and notice; the 500-message budget counts that call's subtree only (a method with hundreds of other calls still expands it), the whole diagram stays under the 2 000-message render limit; the 12 levels count from that call (it goes all the way down a deep call chain). |
| FR-3.8 | S | **The new calls come into view** after an expand the user started (⊕, Expand all, One more level, Smart expand, Expand all below, a fragment's ⊕): when none of the new calls is on screen (they opened below the fold or far to the right), the view scrolls to the first of them, sideways too; a new call already in sight — nothing moves, the clicked ⊕ stays under the mouse (FR-10.5). Renders the user did not start (background scans, refreshes) never scroll. |
| FR-3.4 | M | Recursion is detected: a message whose target is already on the current expansion path is marked recursive and not expandable further. |
| FR-3.6 | S | **Smart expand** = **✦ Overview** (FR-3.12; toolbar ✦, message menu *Show from here ▸ Overview*): expands the important calls first until nothing worth opening is left (or the diagram, or the subtree, reaches the cap, FR-3.10). A call's importance comes from static signals already analysed: ↑ crossing a layer, a port/service/repository/… target (or an interface), an implementation choice, fan-out; ↓ logging, mapping/formatting, getters, constructors, library calls. A collapsed call is worth expanding by its own importance plus what it reveals (the notable calls of its body, scored from the cached one-level look-ahead) — calls that reveal nothing notable stay collapsed. Afterwards low-importance calls are dimmed and every call's tooltip lists the reasons, until *Collapse all*. Tunable in `.seqcall.json` (`smartExpand.budget` = the cap, `important` / `unimportant` globs on `Class.method`). |
| FR-3.9 | S | **Smart expand follows the main path** — the path that runs to the end of the method without failing or bailing out: a call off it is not opened (FR-3.11: its branch folds away), and what such calls would reveal does not make their method worth opening. Off the main path are: a `catch` clause; a branch that throws; a **guard clause** — an `if` branch that only bails out: it returns early without work of its own (no project call but logging or building the error), without a success value (`Status.Ok`, `'success'`, `Success(…)`) and without handing over to project code — except to a helper that only builds a failure (`if (integration is null) return UnsupportedCarrier();` where `UnsupportedCarrier` is `Failure(new …Error(…))`); not inside a loop (a return there is often the success: found, done), not on a dispatch on a variant (`kind == Kind.Express`, `Type::CONST`, `x is Circle c`, a `switch` case), not on a success check (`if (sent.IsSuccess) return;` — what follows handles the failure; "no error", `error == null`, counts as one) — a branch that returns a failure is off the path in any case (`null`, `false`, `[]`, `NotFound()`, `Result.Fail(…)`, a 4xx / 5xx status, a response with an error); a branch that **builds an error** — creates an `…Error` / `…Exception` or calls `Failure(…)`, `Fail(…)`, `NotFound(…)`, `abort(…)` — also in a conditional of the last return (`return ok ? resolved : Failure(…)`); a branch whose condition checks for a failure (`!result.ok`, `status != Status.Ok`, `IsFailure`, `e instanceof FooError`, a negated `Try…`); the `else` of a success check, and the branch beside one that calls `Success(…)` / `Ok(…)` (`credentials is null ? MissingCredentials() : Success(…)`). A missing value without an exit (`if (user == null) user = Create();`) and business variants (`shipping == Express`, FR-1.22) stay on the path. Judged by all three adapters from the guards, the early exits (FR-1.15, with the returned expression) and the calls of each branch, no data flow. Expand all and opening by hand are unchanged (example: [req-examples/FR-3.9](req-examples/FR-3.9.md)). |
| FR-3.10 | S | **Smart expand stops by itself**: it opens what is worth opening and stops when nothing is left, not at a fixed number of messages; the budget is a cap (default 100, `smartExpand.budget`). When the cap stops it with calls still worth opening, a closable notice says so — "Smart expand stopped at 98 messages (limit 100) — 4 important calls still folded (⊕)" — with **Continue** (another cap's worth, most valuable first) and **Collapse all**. |
| FR-3.11 | S | **Smart expand folds the error branches**, at every level (the root's body too): their calls leave both diagrams and each branch keeps one short trace — a branch that throws or returns early its exit marker (FR-1.15), `↯ [!order.isValid] ValidationException ⊕ 2 calls`; a `catch` a branch marker after the try block that says what it does with the error (FR-1.17; amber when it swallows it), `⤷ [catch DbException] ⊕ 1 call`, `⤷ [catch Exception] logged, swallowed` (a clause that only rethrows without calls hides nothing: no marker); any other a half-row branch marker `⤷ [credentials is null] ⊕ 1 call`. Frames that only stated a condition the main path takes go: a `try` whose catches all folded (one catch shown again brings the frame back, the others as its rows), an `alt` whose other branches all folded, an `opt` around a success check (`if (result.IsSuccess)`) — unless it returns from inside: then what follows it is the failure, and the frame keeps saying so. Clicking `⊕ n calls` shows that branch again (its frame comes back) — its calls drawn, dimmed, not opened by Smart; *Expand all* ends the smart view and shows everything; *Collapse all* forgets the branches shown again. Only with **Fragments** on (without frames there is no trace). Kept per diagram like minimized fragments (refresh, focus, re-root, shared states). |
| FR-3.12 | S | **Two separate controls: how calls are opened (✦ ▾) and which paths are drawn (↯)**. **✦ Overview** — Smart expand (FR-3.6 / 3.9 / 3.10): the important calls on the success path; the click always runs it. Its **▾**: *Overview*, *Expand all* (FR-3.3), *Changes* (only during a review with changes in the flow, FR-24: only the paths to the changed methods, walked as the review tour walks them, FR-24.10; a path needing another implementation than an earlier one stays closed, the call counts its changes, FR-24.15), then *One more level* and *Collapse all*. **Overview, Expand all and Changes start from closed**, so each draws the same diagram whatever was open before; *Continue* (FR-3.10) and *One more level* add to what is open. **Show from here ▸** in a call's menu: Overview / Expand all / Changes below that call only — its subtree starts from closed, the rest stays (Shift+click ⊕ = Expand all from here). **↯ Fold errors** (toolbar toggle, pressed = on; also in View ▾ and the canvas menu; a saved and shared option, **on by default**): the error branches (FR-3.9: catch, a branch that throws, a guard clause returning early) fold into one-line markers (FR-3.11) at every depth and in every way of opening — Expand all opens only what is drawn. ↯ hides, it never collapses: a call opened inside a branch is open again when ↯ goes off; ⊕ on a marker shows that branch (an exception, forgotten when ↯ is toggled). Overview ranks the success path whatever ↯ says: with ↯ off the error branches are drawn, dimmed, not opened. A call reached on purpose inside a folded branch — a Find hit (FR-23), a review change or step (FR-24) — shows its branch. The review's list of changes is built with the branches unfolded (the same count with ↯ on or off) and the base flow folds like the current one. Kept by the resets: chosen implementations, followed cases (FR-1.22), minimized frames, filters, layer folds; the steps before the root (FR-8.7, FR-18.14) are not reset. Scans (findings, review, I/O) always see the whole flow. Protocol: `DiagramOptions.foldErrors` (absent = on), `smartExpand.view: 'changes'`; dev host verbs `foldErrors[:off]`, `changes[:id]`. Overview scores with what a fresh open knows — the bodies the background I/O scan reads from the start (four levels below the drawn calls) and the calls drawn — not with what an earlier expansion left in the cache: the bodies, implementations, error-path tests and I/O badges it reads are limited to those, so Overview gives the same result before and after *Expand everything*. |
| FR-3.5 | S | No expand affordance when expanding would show nothing: the target's body is analysed one level ahead and the ⊕ is omitted if it has no calls, or only library calls (while hidden) / calls hidden by filters. An already expanded message keeps its ⊖ until collapsed. |

## FR-4 Callers / references (re-rooting)

| ID | Pri | Requirement |
|---|---|---|
| FR-4.1 | M | Right-clicking any message (found or nested) offers **Show callers**, which lists all references to the message's target method (enclosing method, file, line, code preview). TS: calls through a local the method was destructured into count too (`const { fetchInfo } = useStore(); fetchInfo(id)`, also renamed `{ fetchInfo: f }`). A getter's callers are the reads of its property (`this.orders.toSorted(…)`, `...this.orders`), a setter's the assignments. A call through a cast counts (`(s.save as any)(4)`, `<any>`, `satisfies`). A method is called through itself, an interface / abstract member it implements or a base class's method it overrides — not through a sibling implementation (`d.save()` on a `DbStore` is no caller of `MemStore.save`); an interface member's callers are the calls through the interface. |
| FR-4.2 | M | Choosing a caller re-roots the diagram at the caller's enclosing method; the path down to the call to the previously focused method is expanded automatically so the developer keeps context. |
| FR-4.3 | S | Navigation history: *Back* / *Forward* toolbar buttons restore previous roots together with their expansion state. |
| FR-4.4 | S | **Callers in tests** are hidden by default: the callers panel lists production callers and offers **Include tests (n)** (references in `testFiles` globs), remembered like the other options (`includeTestCallers`); included test callers are tagged `test` and listed last. ## FR-5 Create messages

| ID | Pri | Requirement |
|---|---|---|
| FR-5.1 | M | `new X(...)` is drawn as a «create» message (dashed, open arrow) pointing at the head of the created participant, which is placed at the vertical level of the creation; its lifeline starts there. |
| FR-5.2 | M | The created participant also appears in the top header, rendered faded, so the header lists every participant. |
| FR-5.3 | S | Expanding a create message shows the constructor's calls. |
| FR-5.4 | S | **A call on a new object goes to that object**: `new X().m()` (TS, C#) / `(new X())->m()` (PHP) sends `m` to the participant the creation just made — not to a second `:X` standing for the expression. | FR-5.5 | S | **Every creation is its own object**: objects that are only created (never called afterwards, e.g. result / DTO records) each keep their own head and lifeline (two objects drawn as one would mislead). Fewer columns on request: FR-5.13 (off by default). |
| FR-5.6 | S | **Mutually exclusive creations share a lifeline**: objects of one class created in one activation that can never coexist in a run — each inside an early `return` / `throw` (nothing after it runs: `if (…) return (null, new OrderResult { … }); … return (id, new OrderResult { Ok })`), in different branches of one `alt`, in different `catch` clauses of one `try`, or the try block's last call against a catch (when the catch runs the try block did not finish, so its object never left it) — are drawn on one lifeline: the box says *one of n* (tooltip: why), each «create» says *Alternative i of n* in its hover card. | FR-5.7 | S | **The object a call returns is the caller's object**: `$order = $this->make($vip)` with `make` expanded — every one of its returns creating an `Order` (after FR-5.6 one lifeline) or returning what an expanded call of its own returns (`return $this->factory->make()`, followed down) — so the caller's later calls on `$order` in that activation go to that object, not to a separate `$order` participant. | FR-5.8 | S | **Returned objects through variables, tuples and destructuring**: FR-5.7 also follows a returned local variable (`var o = new Order { … }; return (o, Status.Ok);` — the object the body assigned to it; every assignment we see must give the same object), tuple / array literals element by element (C# `return (o, ok)`, TS `return [o, ok]`, PHP `return [$o, 'ok']`) and the caller's positional destructuring (`(var o, status) = await PlaceOrderAsync(…)`, `const [o, status] = …`, `[$o, $status] = …`), so later calls on `o` — also through a parameter it is passed to — go to the created object. `null` / `default` returns are no object (an early `return (null, status)` does not make it unknown). (example: [req-examples/FR-5.9](req-examples/FR-5.9.md)) |
| FR-5.10 | S | **Interchangeable objects on one lifeline** (TS): objects that cannot differ are drawn on **one lifeline**, marked `×n` (n creations drawn; tooltip says why). | FR-5.11 | S | **Inherited methods**: a call of a method that a project **base class** of the receiving object declares (not overridden; also `base.X()` / `super.x()` / `parent::x()`) stays a call on that object (a self call for `this`) — one object, one lifeline, as UML says — and gets a muted **↑** before the name; the hover card says `↑ inherited: declared in BaseHttpClient`. Creations are not marked. | FR-5.12 | S | **Values on one lifeline** (C#): created objects whose class cannot change once built — a `record`, or only `readonly` fields and get / `init` properties, no instance event, no field of an array or a mutable collection, not `IDisposable`, a base class that is `object` or such a class in the solution (the sidecar's `ClassInfo.immutable`) — share **one lifeline per class**, marked `×n`; the tooltip says why (only their values differ, each call shows them). | FR-5.13 | S | **One lifeline per helper type** (View ▾ option, **off by default** — FR-5.5 is the default): objects of one class created in the drawn calls and never stored in a field (`new OrderQuery(shop).run(db)` three times, a local formatter) share **one lifeline**, marked `×n`, and each «create» on it is numbered (`«create» #2`); the tooltip says they may hold different values. Objects of the class that call or create one another keep their own lifelines (one lifeline would draw a self call or an object creating itself); an object stored in a field (`this.last = new Order()`) is not a helper. ## FR-19 Design findings

Short, clickable markers for likely design flaws in what the diagrams show (not a metrics dashboard), computed in
one pass over data the session already has — no adapter requests. Configurable in `.seqcall.json`:
`"findings": { "maxDependencies": 6, "disable": ["layer-ping-pong"], "ignore": ["Helpers.format", "*Cache*"] }`
(globs on `Class.method` / class names). View ▾ → *Design issues* turns them off.

| ID | Pri | Requirement |
|---|---|---|
| FR-19.1 | S | **I/O in a loop (N+1)**: a call inside a loop over a collection (`foreach`, `for…of`, each-callbacks such as `->each` / `array_map`; polling / retry `while` loops excluded) that does remote I/O (DB, CACHE, HTTP, MQ, CLOUD) itself or below it. When the I/O is only in calls not opened yet it is **"Possible I/O in a loop"** (it may run only on a cache miss, which static analysis cannot see). I/O reached only through a **load-once branch** — a field tested for "not set yet" (`if (!self::$loaded)`, `!isset(static::$cache[$k])`, `$this->client === null`, `if (!this.cache)`, `_x is null`) — runs once and does not count (example: [req-examples/FR-19.1](req-examples/FR-19.1.md)). ## FR-31 Unreachable code

Which methods of the project no entry point reaches: candidates for deletion, or code the analysis cannot see being
called (a framework calling it by convention). Project-wide, on request.

| ID | Prio | Requirement |
|---|---|---|
| FR-31.1 | S | **The scan**: the project's methods (classes and module functions of its own files, with a body, not in test code; adapter `getProjectTypes`) minus those reached from the entry points (FR-16.1, tests excluded) over the call graph — every call's target, all implementations / overrides of a reached method, methods passed as an argument (FR-1.13) and the calls of lambdas passed as one, a route's middleware (FR-18.14), for a call on a type the container binds the bound class's method of that name (FR-8.6; also when the class does not implement the type), and module-level code (TS: `export const shopModule = withAudit(shopRoutes)` runs when the module loads; adapter `getModuleCalls`). The constructors of a class are walked when one of its instance methods is reached or it is created (DI creates objects without `new`; what a constructor calls — an event subscription — runs with it); a project class named as a library call's type argument is created by the library (`AddScoped<IShop, Shop>()`; `UseMiddleware<AuditMiddleware>()` also runs its `Invoke` / `InvokeAsync`). A constructor that only stops others from creating the class (non-public, no parameters, the class's only one, calling nothing) is not listed. Each method left gets its reason: **no callers**, **called only from unreached code** (from the unreached methods' own calls), **only tests call it** (the references query, FR-4.4). A method a reached method, a closure / local function or a value use refers to (kept in an object or array, assigned; C#: a method group assigned to a property or field, added to an event, returned — `options.InvalidResponse = ErrorFactory.Create`, which the framework calls later; adapter `getValueUses`; not imports / exports, not `nameof` or doc references) is *probably reached*: not listed, counted, and the walk goes on from it in another round. A project without entry points (a library) lists nothing. Kept across saves (the walk is slow and a save rarely changes what is reached), marked *The code changed since this check … ↻* (changes in what is called show after ↻); a changed `.seqcall.json` drops it. Cancellable, with progress. A file saved while the walk runs: the list is shown with *The code changed while this ran … ↻ checks again* and not kept (the next request walks again). |
| FR-31.2 | S | **Probably called by the framework**, listed apart: magic methods (`__toString`, `__invoke`), methods the runtime calls by name (`toString`, `toJSON`, `ToString`, `Equals`, `Dispose`, `jsonSerialize`), methods of a class extending / implementing a library type (`extends Model`, `implements ShouldQueue`; also through the project's own base classes, up to six levels: *extends AbstractValidator, through OrderValidatorBase*; not for private methods) — with that reason — and what those reach, their classes' constructors included (a console kernel's schedule, a service provider's boot): *called from Kernel.schedule, which the framework calls*. |
| FR-31.3 | S | **Maybe called**, listed apart: a listed method whose name a call the analysis could not resolve has — in reached code (an untyped receiver, a facade; lambdas included) or in a template it does not parse (Laravel Blade views: `->name(`, `::name(`, `name(`; adapter `getTemplateCallNames`) — with how many such calls, and what it reaches with it (*via Shop.render*). Calls in unreached code do not count. The PHP references query shares its scan between methods of one name (cleared when a file changes or package files load). |
| FR-31.4 | S | **Methods a tool runs by convention**: `"unreachable": { "ignore": ["database/migrations/**", "*Listener.handle"] }` in `.seqcall.json` — globs on the file (relative path) or on `Class.method`; those methods are walked from like entry points (what they call is reached), counted, not listed. |
| FR-31.5 | S | **CLI / MCP `seqcall unreachable`** (FR-27): the groups as text (*no callers*, *called only from unreached code*, *only tests call it*, *maybe called — …*, *probably called by the framework*), each method with file:line and its note; a summary line (`unreachable: 34 of 72 methods (from 15 entry points, tests excluded); 2 probably reached …; 3 ignored by the config`); a library says so instead of listing everything; `# INCOMPLETE` when the walk hit its limit. JSON: the rows with key, reason, callers, framework, unresolved, via. MCP tool `unreachable`. |
| FR-31.6 | S | **The panel** (all editors, the webview): **∅ Unreachable** in ⌂ Entry points (VS Code also *Seqcall: Show Unreachable Code*) — progress per phase (*Following the calls from the entry points… n methods*, then *Checking what no entry point reaches… n / total* with a bar) and *Cancel*; then the summary, a filter (method or file words), the groups (at most 200 rows each, the rest counted), one line per method (name; file:line · callers / unresolved calls · via / the framework reason); a row opens the method's declaration; *Copy as Markdown*; **↻** scans again. Cached until a file changes. |

## FR-32 Entry point outcomes

What an entry point touches and how it can end, without reading its flow: the I/O of the whole flow (database, other
APIs, files, queues …); the exceptions that reach the caller and the HTTP statuses (C) follow once they can be found
reliably. Shown for entry points only (FR-16); nothing project-wide runs without a request.

| ID | Prio | Requirement |
|---|---|---|
| FR-32.1 | S | **Outcome of a flow**: for an entry point, the I/O of its **whole** flow — every call below it, also those not expanded in the user's diagram, interface calls as in FR-17.6 — by kind (FR-17 kinds, same order), each kind with the project classes whose bodies do it (the `in X` of the I/O evidence: `HTTP via PaymentGatewayClient, ShippingApiClient`), each class with its library calls and file:line. Computed in the background session that already opens the same flow fully expanded for the design issues — no extra walk; error branches included (↯ Fold errors off). A call is listed once per place, with its file:line. A body is charged to the object that runs it, also below a folded call or behind an interface: a base class's method called on `this` / `base` to the calling object (`HTTP via ShopClient`, not `BaseHttpClient`, FR-5.11), an interface method to its implementation's class, any other call to its method's class. *At least* when the flow was not followed to its end: a call left folded with calls of its own (the expand limit, a "don't expand" rule), an interface call with more implementations than the I/O walk follows (FR-17.6), or I/O deeper than the walk goes (FR-17.5: 4 levels, 200 methods, a body not analysed) — it says which: *at least: 3 calls left folded, OrderHandler.handle has 22 implementations, the I/O walk stopped at OrderClient.post* (two of each named, the rest counted). Hiding a call does not change it (its I/O counts through its body, as FR-17). Unresolved calls are counted (*3 calls not resolved*). [Example](req-examples/FR-32.1.md) |
| FR-32.2 | S | **Shown at the gate**: on the found message, after the method name, the flow's I/O kinds in the I/O colour, muted: `⇢ HTTP · FILE` (`+` when *at least*, `⇢ no I/O` when none was found) — on the same row, so nothing moves when the background scan brings it (no row is reserved or added); a long label crosses the first lifeline over its backdrop, as other labels. Its hover card (the found message's, under *Entry point*): *What the whole flow touches (I/O)*, per kind the classes, under each its calls with file:line (3, then *+n more*; a click opens the line, FR-2), why it is *at least* (FR-32.1), the calls not resolved. Drawn in the image export (FR-25.1) as part of the label; gone with the I/O toggle off (FR-17.4). |
| FR-32.3 | S | **When**: in the background after the first render of an entry point's diagram, after the I/O scan (FR-17.5); the diagram is never delayed, a second render adds the line. Kept per flow until the code changes; after a change it is computed again by the next background scan (the line is gone until then). Expand, collapse and zoom do not change it (it describes the flow, not the drawing). Re-rooting on a method that is no entry point drops it; Back restores it (as FR-16.3). |
| FR-32.4 | S | **Badges in the entry-point lists** (⌂ panel, VS Code sidebar, Go to Entry Point FR-16.9): a row shows its I/O kinds as small pills once its outcome is known — from FR-32.3 for the entry points opened, and for all of them after the project-wide design-issue scan (FR-19.9), which already expands and I/O-scans every flow (no scan of its own). The ⌂ filter (FR-16.15) and Go to Entry Point take `has:http`, `has:db` … (a kind or its tag: `has:mq`; `has:io` any I/O); an entry point whose outcome is not known yet does not match, and the method search (FR-16.15) leaves the `has:` words out. Pills: `DB·HTTP` (VS Code: beside the method), `+` when the outcome is *at least*; a flow without I/O shows none. A code change forgets the outcomes of the flows that saw the old code. Before a scan a row shows nothing (unknown is not "no I/O"). |
| FR-32.5 | S | **CLI / MCP `seqcall outcomes [<words>…]`** (FR-27): per entry point (filtered like `entrypoints`) its label and I/O kinds with the classes doing them, library calls and file:line with `--detail`; a summary line (`outcomes: 40 entry points (tests excluded), 31 with I/O — db 28, http 12, file 2`), a row not followed to its end says why (FR-32.1), and these flows are counted as a limit (`# INCOMPLETE`); text and `--format json` (FR-27.2), short by default (FR-27.6); also an MCP tool (FR-27.7). One walk with `issues` (the project scan, kept until the code changes). |
| FR-32.6 | C | **Exceptions that reach the caller**: thrown in the flow and not caught on the way up to the entry point (a `catch` matching the type or a project base type stops it; a rethrow passes it on), each with where it is thrown; needs propagation along the call paths. |
| FR-32.7 | C | **Statuses and results**, per framework: ASP.NET (result helpers, `ActionResult<T>` / a returned DTO → 200, `[ProducesResponseType]`), Fastify / Express / Nest (route schema `response`, `reply.code`), Laravel (`abort`, `response()->json(…, n)`), and the project's global exception handler mapping exceptions to statuses. ## FR-33 Seqcall in the editor's hover

What the analysis knows about the code under the cursor, where the developer reads code: which implementation a call
really runs (the IDE knows the interface, the DI container knows the class), what it touches, who reaches a method.
Answered by the core, shown by the hosts; only what says something.

| ID | Prio | Requirement |
|---|---|---|
| FR-33.1 | S | **The call under the cursor**: the innermost call whose range holds the position (calls inside a lambda passed as an argument too), and only a call named like the word under the cursor (a creation: its class name) — a hover on an argument or a variable is no hover on its call. Else, on a method's name (its declaration line), that method. Nothing else gets a hover. |
| FR-33.2 | S | **What runs at a call** whose target has no body (an interface or abstract member), decided as the diagram decides it without a path from an entry point: the object created in the same method (`new X()` then `x.m()`, `new X().m()`), the class's own override (`this.m()`), the DI container's binding (FR-8.6; an injected field: its class is the consumer; the call's type arguments pick a generic registration; with several apps only when all of them bind the same class) with the registration's file:line, else the only implementation (setting `autoSelectSingleImplementation`) — `→ runs SqlRepo.save (the DI container binds it, Program.cs:42)`. Otherwise up to five candidates and `+n` (`(the caller decides)` for a parameter) and the keyed / conditional registrations (`→ chosen at run time: Maps ("maps")`). **Its I/O** (FR-17): a library call's own (`↯ DB`), else what runs below the implementation that runs, or what all candidates share (`↯ HTTP below`). |
| FR-33.3 | S | **On a method's name**: the entry points its callers lead to (FR-22 walk; up to five, `+n`, the test methods among the callers counted, *more paths not followed* when a limit cut the walk) — a heading with the counts, `⌂ reached from 14 entry points · 116 tests`, then one entry point per line (a list in code font in VS Code; the last line `+9 more`); `⌂ only tests reach it (n)` when no entry point does; `∅ no entry point reaches it: <group>` when the last unreachable-code scan (FR-31, not stale) lists it; the I/O its body does, itself or below. No line for "nothing found". |
| FR-33.4 | S | **Fast enough for a hover**: the bodies and callers come from the session's caches; a part not worked out within the budget (default 400 ms) goes on in the background and is kept until the code changes (`⌂ still looking for callers… (ask again in a moment)`); the next hover has it. Never changes the user's diagram. The hover text is one core function (`codeInfoLines`) for every host. |
| FR-33.5 | S | **VS Code**: a hover provider for TS / JS / C# / PHP files on disk; only for a project already loaded (a hover never starts the analysis — the background load, FR-16.10, usually has) and only for a saved file (the analysis reads the disk). **Seqcall** heading, the lines, then the links *Sequence diagram* (the method the cursor is in) and, on a method's name, *Paths to here* (the diagram, then its paths-to-here panel on the root). Setting `seqcall.hover` (default on). |
| FR-33.7 | S | **From an entry point in the hover to its flow**: each listed entry point is a link that opens its sequence diagram expanded along its shortest path down to the method, the method highlighted (as a row of Paths to here does, FR-22); `+n more` opens a list of all of them (VS Code quick pick, filterable by route or kind; each row says how many calls down), whose first row *Show all in Paths to here* opens the whole caller tree. The paths come from the hover's own walk (`CodeReach.routes`), no extra analysis. |
| FR-33.6 | S | **Rider / PhpStorm and Vim / Neovim — Info at Caret**: the same lines through the stdio host (`describeAt`: the lines, the same with the items numbered, every entry point's label, whether the caret is on a method's name; asked explicitly, so it loads the project when needed and waits up to 8 s before a part shows as still running). Rider: *Seqcall: Info at Caret* (editor context menu; no default shortcut — assign one in Keymap) shows them in a popup at the caret, the entry points as links (each opens its flow down to the method in the tool window, *+n more* a searchable list whose first row is *Show all in Paths to here*), *Sequence diagram* · *Paths to here* below; a real mouse hover is not possible there (C# quick documentation belongs to the ReSharper backend). Vim / Neovim: `:SeqcallInfo` (mapping `<Plug>(seqcall-info)`) in a popup / floating window at the cursor, the entry points numbered; `:SeqcallReach n` opens one's flow in the page, `:SeqcallReach` lists them all (last row *Show all in Paths to here*). |

## FR-34 Memory

How much memory Seqcall's analysis takes, and a way to give it back without restarting the editor. Only what can be
measured exactly: a process Seqcall started (the C# sidecar); TS / JS and PHP run inside the editor's extension host,
shared with other extensions, so their share is not measured.

| ID | Prio | Requirement |
|---|---|---|
| FR-34.1 | S | **The C# sidecar reports its memory** (`getMemory`: process id, working set, .NET managed heap). Asked only while it runs — measuring never starts it; no answer within 5 s: not known. During a review the base version's sidecar (FR-24.6) is reported too. |
| FR-34.2 | S | **Free memory**: per loaded project, the session's caches and kept scans are dropped (as a refresh without changed files: bodies, callers, entry points, the design-issue / map scans, the unreachable list, hover parts) and the C# sidecar(s) stopped; the next request starts the sidecar again (the solution loads again, seconds). The diagram on screen stays; the next step rebuilds from the code. The TypeScript program and the PHP index stay (every answer needs them). |
| FR-34.3 | S | **VS Code**: *Seqcall: Show Memory* writes one line per loaded project to the "Seqcall" output channel (`sample-cs (C#): C# analysis 812 MB (managed heap 410 MB), pid 1234`; TS / PHP: *runs in the extension host, shared with other extensions — not measured alone*; C# not running: *not loaded*) and shows a short notification with **Free Memory**; *Seqcall: Free Memory* frees and says how much the stopped sidecars held. |
| FR-34.4 | S | **Rider / PhpStorm and Vim / Neovim**: the stdio host is a process of its own, so its memory is exact (the TS / PHP analysis and the diagrams): `memory` gives one line for it and one per loaded project (the C# sidecar as in FR-34.1) and a summary (`Seqcall uses 420 MB, the C# analysis 812 MB.`); `freeMemory` as FR-34.2. Rider: *Tools → Seqcall: Show Memory* (a notification with the lines and **Free Memory**) and *Seqcall: Free Memory*; Vim / Neovim: `:SeqcallMemory` (the summary; the lines in `:SeqcallLog`) and `:SeqcallFreeMemory`. |
